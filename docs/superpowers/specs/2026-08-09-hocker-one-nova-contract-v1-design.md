# Hocker One ↔ NOVA Contract v1 — Design

Date: 2026-08-09 (America/Tijuana)  
Status: approved architecture; implementation pending written-spec review  
Canonical owner: `HockerAGI/nova.agi`  
Consumer: `HockerAGI/hocker.one`

## 1. Purpose

Create one machine-readable, versioned contract for the private service boundary between Hocker One and NOVA. The contract must stop request, response, error, streaming, evidence, and Owner Gate behavior from drifting independently across the two repositories.

The contract describes the private server-to-server interface. It does not expose provider, model, internal evidence identifiers, or infrastructure details to the browser. Hocker One remains responsible for sanitizing the private NOVA response before returning a public response to the signed-in user.

## 2. Ownership and distribution

NOVA owns the canonical contract because NOVA provides the API. Canonical files live in:

```text
contracts/hocker-one-nova/v1/
  request.schema.json
  success.schema.json
  error.schema.json
  sse-event.schema.json
  manifest.json
```

Hocker One vendors an exact snapshot in:

```text
contracts/nova/v1/
  request.schema.json
  success.schema.json
  error.schema.json
  sse-event.schema.json
  manifest.json
  UPSTREAM_MANIFEST_SHA256
```

`manifest.json` records the contract identifier, semantic version, JSON Schema dialect, canonical repository and path, and a SHA-256 digest for every schema file. Hocker One additionally stores the SHA-256 of the exact upstream manifest. CI verifies all file digests and rejects any unreviewed drift.

This design deliberately avoids a new npm package or third repository. A shared package can replace vendoring when three or more independently deployed consumers need the contract.

## 3. Versioning and compatibility

Contract identifier:

```text
hocker-one-nova.chat
```

Initial semantic version:

```text
1.0.0
```

Conforming requests send:

```http
X-Hocker-Nova-Contract: 1.0.0
```

NOVA returns the same header on success and contract-aware errors. The JSON response also includes `contract_version` so stored evidence remains self-describing after HTTP headers are gone.

Compatibility rules:

- Patch: clarifications and new optional values that do not invalidate existing v1 payloads.
- Minor: additive optional fields or new error codes; old consumers remain valid.
- Major: removed or renamed fields, changed meaning, newly required fields, or changed Owner Gate invariants.
- Unknown major versions return HTTP 409 with `CONTRACT_VERSION_UNSUPPORTED`.
- During the first rollout only, NOVA continues accepting a missing version header for legacy callers and marks the request as legacy in audit metadata. Hocker One sends the header immediately after adopting the snapshot.
- Strict rejection of an absent version header is a separate rollout step after the production smoke proves that every Hocker One environment sends v1.

The deprecated `text` request alias remains accepted by NOVA during v1 compatibility but is not part of the canonical request schema. Hocker One sends `message` only.

## 4. Authentication and trust boundary

The private NOVA endpoints require:

```http
Authorization: Bearer <NOVA_ORCHESTRATOR_KEY>
Content-Type: application/json
X-Hocker-Nova-Contract: 1.0.0
X-Hocker-Source: hocker.one
X-Request-ID: <uuid>
```

Rules:

- Hocker One authenticates the human session and project membership before calling NOVA.
- Hocker One overwrites client-supplied `user_id`, `user_email`, `project_id`, runtime policy, and queue state with server-derived values.
- NOVA authenticates Hocker One with a timing-safe Bearer comparison.
- Neither repository logs the Bearer value, cookies, raw OIDC token, or privileged environment variables.
- `X-Request-ID` is generated by Hocker One and echoed by NOVA for correlation. NOVA also generates a distinct `trace_id` for the model execution.
- Rate limiting fails closed if its persistent state is unavailable.
- The browser never calls NOVA directly.

## 5. Request contract

Canonical operation:

```http
POST /api/v1/hocker/chat
```

This dedicated private endpoint is necessary because the existing `/chat`, `/api/chat`, `/api/v1/chat`, and `/api/v1/nova/interact` aliases intentionally cloak provider and model metadata. They remain backward-compatible, bearer-protected, cloaked legacy aliases. Hocker One moves to `/api/v1/hocker/chat`, which returns the private audit fields required by this server-to-server contract. Creating a dedicated endpoint avoids weakening the public-response cloaking guarantees of existing aliases.

Canonical request fields:

| Field | Type | Required | Contract meaning |
|---|---|---:|---|
| `contract_version` | string constant `1.0.0` | yes | Persisted representation of the negotiated contract. |
| `project_id` | string matching `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$` | yes | Project already authorized by Hocker One. |
| `thread_id` | UUID or null | yes | Existing memory thread, or null to create one. |
| `message` | string, 1–100000 chars | yes | User message after transport validation; content is not treated as authorization. |
| `prefer` | constant `auto` | yes | Provider selection belongs to NOVA. |
| `mode` | constant `auto` | yes | Effective mode is selected by NOVA policy and intent. |
| `allow_actions` | boolean | yes | Permission to propose/defer candidate actions; never permission to execute writes. |
| `user_id` | string or null, max 128 | yes | Server-derived authenticated user identifier. |
| `user_email` | email or null | yes | Server-derived email used only where policy permits. |
| `context_data` | object | yes | Bounded runtime context; arbitrary nested values are allowed only beneath documented extension points. |

`context_data.hocker_runtime` is required and contains:

- `contract_version`
- `source` equal to `hocker.one`
- `queue_lock`
- `capabilities_contract`
- `execution_policy` equal to `owner_gate_only`
- `public_provider_cloaking` equal to `true`

`queue_lock` contains at least:

- `locked`
- `can_start_new_task`
- `blocking_count`
- `reason`
- `source`

Request limits:

- Fastify body limit remains 512 KiB.
- Oversized payloads return the canonical `PAYLOAD_TOO_LARGE` error.
- Unknown top-level fields are rejected. Extension data belongs under `context_data.extensions`.

## 6. Success response contract

The private success response uses HTTP 200 and contains:

| Field | Required | Meaning |
|---|---:|---|
| `ok: true` | yes | Successful model completion and response construction. |
| `contract_version` | yes | `1.0.0`. |
| `project_id` | yes | Authorized project. |
| `thread_id` | yes | Persisted thread UUID. |
| `reply` | yes | NOVA public-language answer. |
| `intent` | yes | Classified intent. |
| `agi_id` | yes | Internal specialist selected under NOVA. |
| `actions` | yes | Always empty in NOVA v1; writes are not enqueued by NOVA. |
| `trace_id` | yes | Model execution correlation UUID. |
| `provider` | yes, private | Actual provider for audit and usage. |
| `model` | yes, private | Actual model for audit and usage. |
| `meta` | yes | Evidence, MCP, controls, persistence, and context metadata. |

`meta.evidence` contains:

- `user_message_id`: UUID or null
- `assistant_message_id`: UUID or null
- `syntia_memory_persisted`: boolean
- `syntia_memory_event_id`: UUID or null
- `usage_persisted`: boolean
- `usage_id`: UUID or null
- `provider`
- `model`
- `trace_id`

Persistence failures do not masquerade as successful persistence. The completion may still return HTTP 200 if the answer exists, but every failed persistence flag is `false` and the corresponding identifier is null. Hocker One surfaces degraded evidence in internal diagnostics without revealing infrastructure details to the browser.

`meta.controls` contains:

- `allow_write: false`
- `requested_actions`: original request signal
- `effective_actions: false`
- `enqueued_actions: 0`
- `action_policy: hocker_one_owner_gate_only`
- `fallback_used`
- `survival_mode`
- `provider_failures`
- `queue_lock`
- `runtime_policy`

`meta.mcp.deferred_actions` may contain validated action proposals. These are data, not executable authorization. Hocker One independently validates and materializes an allowed proposal into `agi_action_queue` with `needs_approval=true`.

Before returning data to the browser, Hocker One removes private `provider`, `model`, provider failures, internal topology, and privileged evidence identifiers from the public payload. It retains them in server-side audit evidence.

## 7. Error contract

All contract-aware errors use:

```json
{
  "ok": false,
  "contract_version": "1.0.0",
  "error": {
    "code": "RATE_LIMITED",
    "message": "Solicitud temporalmente limitada.",
    "retryable": true,
    "retry_after_seconds": 10
  },
  "trace_id": null,
  "request_id": "uuid"
}
```

Canonical codes and status mapping:

| HTTP | Code | Retryable |
|---:|---|---:|
| 400 | `INVALID_REQUEST` | no |
| 401 | `UNAUTHORIZED` | no |
| 409 | `CONTRACT_VERSION_UNSUPPORTED` | no |
| 413 | `PAYLOAD_TOO_LARGE` | no |
| 429 | `RATE_LIMITED` | yes |
| 502 | `PROVIDER_FAILED` | yes |
| 503 | `RATE_LIMIT_UNAVAILABLE` | yes |
| 503 | `PERSISTENCE_UNAVAILABLE` | yes |
| 504 | `UPSTREAM_TIMEOUT` | yes |
| 500 | `INTERNAL_ERROR` | no by default |

Messages are sanitized and stable enough for user-facing translation. Stack traces, SQL messages, provider credentials, raw provider errors, and environment values never cross the boundary.

## 8. Streaming contract

Canonical operation:

```http
POST /api/v1/hocker/chat/stream
Accept: text/event-stream
```

The existing `/api/v1/chat/stream` remains a backward-compatible lifecycle-streaming alias. Hocker One uses the dedicated contract endpoint so version negotiation, private evidence, and client cloaking cannot be confused with the legacy surface.

The request schema, authentication, project boundary, version, Owner Gate policy, and rate limit are identical to non-stream chat.

Allowed SSE events:

1. `accepted`
   - `ok: true`
   - `contract_version`
   - `request_id`
   - `trace_id`
   - `transport: nova_agi_sse`
   - timestamp
2. `heartbeat`
   - timestamp only; no secrets or model content
3. `message`
   - `ok: true`
   - `type: final`
   - final `content`
   - `actions`, empty at the NOVA boundary
   - sanitized `meta`
   - transport
4. `error`
   - canonical error object and HTTP-equivalent status
5. `done`
   - `ok`
   - `trace_id`

Exactly one terminal `message` or `error` is emitted, followed by exactly one `done`. Provider token-by-token streaming is not claimed in v1; v1 is lifecycle streaming with a final message. Client disconnect and the 55-second timeout stop upstream work where possible and do not produce duplicate terminal events.

Hocker One must apply the same authenticated project-role check to its public stream proxy as it applies to non-stream chat. A contract test proves that unauthenticated streaming cannot reach NOVA.

## 9. Owner Gate invariants

These rules are normative and cannot change in a v1 patch or minor release:

1. Text, prompt content, model output, MCP output, and `allow_actions=true` are never authorization to write.
2. NOVA may execute explicitly read-only MCP tools.
3. NOVA does not insert executable chat actions into `agi_action_queue`.
4. NOVA may return validated deferred proposals in `meta.mcp.deferred_actions`.
5. Hocker One revalidates project, actor role, tool, action type, payload, risk, queue lock, and idempotency before materialization.
6. Materialized writes enter Hocker One as `needs_approval=true`.
7. Only Owner Gate can approve or reject.
8. Only the approved executor may perform the write.
9. Execution records evidence, result hash, actor, timestamps, error, and rollback information.
10. A fallback runtime preserves the same rules; fallback never weakens authorization.

## 10. Fallback and timeout state machine

Hocker One uses these states:

```text
validate_session
→ validate_project_role
→ validate_contract_request
→ call_nova_upstream (8-second connection/response gate)
  → upstream_success
  → upstream_contract_error (do not hide with fallback)
  → upstream_auth_error (diagnostic failure; do not retry with weaker auth)
  → upstream_unavailable_or_timeout
      → run_hocker_serverless_fallback
          → fallback_success
          → fallback_error
```

Fallback is allowed for unavailability, timeout, or configured provider failure. It is not used to hide contract-version, authentication, authorization, or invalid-request failures. Every fallback response records `runtime_fallback.active`, reason, runtime, and whether upstream was called.

The serverless fallback produces the same public response shape and evidence semantics as upstream NOVA. Provider and model remain private after Hocker One sanitization.

## 11. Directed operational smoke

The general worker endpoint claims the next eligible queue item and therefore is not a safe directed test mechanism. Contract rollout adds a separate internal diagnostic operation or an equivalent server-side reservation mechanism with these properties:

- Requires a one-time, short-lived, purpose-bound token.
- Requires an exact `task_id` created for the smoke.
- Rejects a purpose/mode mismatch instead of falling through to the general worker.
- Claims only that task or returns `TASK_NOT_ELIGIBLE`.
- Requires `write_policy=read_only`, `allow_actions=false`, and `max_attempts=1`.
- Never consumes another production queue item.
- Returns only evidence metadata, not secrets or raw model content.
- Is removed after rollout unless retained as a documented, owner-only operational capability.

This operation is an Hocker One operational control, not part of the public chat schema.

## 12. Contract tests

### NOVA provider tests

- Canonical schemas are valid JSON Schema 2020-12.
- Manifest hashes match every canonical schema.
- Valid v1 requests pass.
- Unknown top-level fields fail.
- Missing `message`, invalid project IDs, non-UUID threads, provider selection other than `auto`, and oversized messages fail.
- Unknown major versions return 409.
- Missing version remains legacy-compatible only during the recorded rollout window.
- Success fixtures validate against `success.schema.json`.
- Every error path validates against `error.schema.json`.
- SSE lifecycle validates against `sse-event.schema.json` and emits one terminal event.
- `actions` remains empty and `effective_actions` remains false.
- Deferred MCP writes are data-only.
- Provider/model cloaking tests confirm private values do not leak through the legacy aliases, while the dedicated Hocker endpoint returns them only to the authenticated server-to-server consumer.

### Hocker One consumer tests

- Vendored schema file hashes and upstream manifest hash match.
- The generated upstream request validates against the canonical request schema.
- Client-supplied identity and runtime policy are overwritten.
- Both chat and stream routes require an authenticated project role.
- The NOVA Bearer and contract headers are sent.
- Success responses validate before sanitization.
- Invalid upstream success payloads fail closed and create diagnostic evidence.
- Public sanitization removes provider, model, provider failures, and privileged persistence identifiers.
- Contract errors map to stable public errors without losing internal request/trace correlation.
- Fallback only runs for allowed failure classes.
- Fallback cannot enqueue or execute writes.
- Deferred actions must pass the existing Hocker One materializer and Owner Gate.
- Directed smoke cannot claim an unrelated task.

## 13. Rollout order

1. NOVA PR: add canonical schemas, manifest, validators, response version/header, canonical errors, SSE conformance, tests, and backward-compatible missing-header audit.
2. Verify NOVA CI and CodeQL; merge NOVA first because it is backward compatible.
3. Hocker One PR: vendor the snapshot, pin hashes, send v1 headers/body, validate private responses, align stream authentication, enforce sanitization, add directed smoke safety, and add consumer contract tests.
4. Verify Hocker One CI, CodeQL, Preview, and a directed read-only smoke against the exact SHA.
5. Merge Hocker One and verify its new production deployment.
6. Execute one directed NOVA smoke from production and verify provider, model, memory, usage, evidence, fallback policy, token consumption, and zero external writes.
7. After all environments show v1 requests, optionally enable strict missing-version rejection in a separate NOVA PR.

At no point does rollout require direct writes to `main`, a production SQL migration, secret rotation, or a temporary weakening of Owner Gate.

## 14. Non-goals

- Moving NOVA to the OpenAI Agents SDK.
- Choosing a single AI provider.
- Exposing provider/model selection to users.
- Creating a new shared npm package or repository.
- Redesigning the Hocker One UI.
- Changing the AGI hierarchy.
- Allowing NOVA to approve or execute production writes.
- Adding new paid infrastructure.

## 15. Acceptance criteria

The contract is complete when:

- One canonical v1 schema set exists in NOVA.
- Hocker One pins an exact, hash-verified snapshot.
- Both repositories fail CI on contract drift.
- Chat and SSE use the same authentication, project, error, evidence, and Owner Gate rules.
- Provider/model are auditable privately and cloaked publicly.
- Memory and usage persistence are represented truthfully.
- Fallback preserves the same authorization boundary.
- A directed smoke can never consume an unrelated task.
- New `main` commits in both repositories are green after merge.
- The final production smoke produces correlated evidence and zero unapproved writes.
